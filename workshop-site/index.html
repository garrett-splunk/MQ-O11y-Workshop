Facilitator guide

Hands-on lab · IBM MQ metrics · Splunk Observability Cloud

IBM MQ metrics in Splunk Observability Cloud

Run a local IBM MQ queue manager, export queue and queue-manager metrics with mq_otel, and view them in Splunk Metrics. Sample apps move messages so queue depth changes; this lab does not cover APM traces or Log Observer in the exercises.

What you will do

Clone the repo, add your Splunk ingest token, start Docker Compose, run the verification script step by step, generate traffic, and chart IBM MQ metrics (especially ORDER.REQ depth).

Step 1~5 min

Prerequisites

  • Docker Desktop running (8 GB+ RAM recommended; Apple Silicon uses linux/amd64 for MQ images)
  • Node.js 20+ and npm (for npm run load-traffic)
  • Git to clone MQ-O11y-Workshop
  • Splunk Observability Cloud access with permission to create an ingest token
  • Accept IBM MQ developer license (LICENSE=accept in Compose — education/dev only)

Clone the lab (once)

Terminal
mkdir -p ~/projects/ibm-mq-o11y-lab
cd ~/projects/ibm-mq-o11y-lab
git clone https://github.com/garrett-splunk/MQ-O11y-Workshop.git .

Ports: 1414 MQ, 8080 producer, 8091 local workshop, 4317 OTLP, 13133 collector health.

Step 2~10 min

Splunk ingest token (.env.splunk)

Only the OpenTelemetry Collector reads this file. It forwards metrics to Splunk using your token and realm URLs.

2a — Create the file from the template

Terminal (repo root)
cd ~/projects/ibm-mq-o11y-lab
cp .env.splunk.example .env.splunk

2b — Get an ingest token in Splunk O11y

  1. Sign in to Splunk Observability Cloud (note your realm, e.g. us1 in the URL).
  2. Open Organization Settings (gear) → Access Tokens.
  3. Choose New Token → type Ingest (not API-only).
  4. Copy the token value once; you will not see it again.

2c — Paste the token and fix the realm

Open .env.splunk in your editor. Update these lines (example for US1):

SPLUNK_REALM=us1
SPLUNK_ACCESS_TOKEN=paste-your-ingest-token-here
SPLUNK_INGEST_URL=https://ingest.us1.signalfx.com
SPLUNK_API_URL=https://api.us1.signalfx.com
SPLUNK_LOG_INGEST_URL=https://ingest.us1.signalfx.com/v1/log

Realm must match

If your org is EU0, use ingest.eu0.signalfx.com and api.eu0.signalfx.com. Never commit .env.splunk to git.

2d — Confirm the file exists (do not print the token)

Terminal
test -f .env.splunk && echo "OK: .env.splunk present"
grep -q 'your-ingest-token-here' .env.splunk && echo "WARN: replace placeholder token" || echo "OK: token line edited"
Step 3~5 min

Lab secrets and application env

The mq_otel exporter connects to MQ as user app. Docker Compose reads the password from a secret file.

Terminal
cd ~/projects/ibm-mq-o11y-lab
cp .env.example .env
cp secrets/mqAppPassword.example.txt secrets/mqAppPassword.txt

Default demo password is in .env.example (MQ_APP_PASSWORD). The file secrets/mqAppPassword.txt must match that value for mq-otel-exporter.

Step 4~15 min

Start the Docker stack

First run builds IBM MQ, Node services, and the mq_otel image. Allow several minutes.

Terminal
cd ~/projects/ibm-mq-o11y-lab
docker compose up --build -d

Wait until MQ is healthy:

Check status
docker compose ps

Expect mq healthy, then mq-otel-exporter, otel-collector, order-producer, and order-consumer running.

If you edited .env.splunk after the stack was already up:

docker compose up -d otel-collector

Step 8~15 min

View IBM MQ metrics in Splunk

  1. Open Splunk Observability Cloud → Metrics (or Chart builder / Metric finder).
  2. Search for metrics whose names start with ibmmq (from metaprefix in mq_otel config).
  3. Filter or group by dimension deployment.environment = ibm-mq-lab when available.
  4. Find queue depth for ORDER.REQ (exact metric name may include queue name as a dimension — browse related series).
  5. Chart queue depth over time while running Step 7 again if the chart is flat.

Metrics to discuss

Queue depth on ORDER.REQ, channel status, connection count — capacity and backlog signals for operations teams.

Detector idea

Create a detector when ORDER.REQ depth stays above a threshold for several minutes.

No metrics? Confirm .env.splunk, restart collector, check docker compose logs mq-otel-exporter and otel-collector.

Step 9~10 min

Failure demo — queue depth (metrics only)

Stop the consumer so messages accumulate on ORDER.REQ; watch depth rise in Splunk Metrics.

  1. Stop the consumer 
    docker compose stop order-consumer
  2. Send load 
    npm run load-traffic -- 25 200
  3. In Splunk Metrics — watch ORDER.REQ depth increase.
  4. Restore processing 
    docker compose start order-consumer
  5. Confirm depth trends down as the consumer drains the queue.

Troubleshooting

No IBM MQ metrics in Splunk

Verify .env.splunk token and realm URLs. Run docker compose up -d otel-collector. Check docker compose logs mq-otel-exporter and docker compose logs otel-collector. Ensure secrets/mqAppPassword.txt exists.

verify-stack.sh fails on health checks

Run docker compose ps and docker compose logs mq. MQ can take ~60s on first start. Re-run the script after MQ is healthy.

Flat queue depth chart

Run npm run load-traffic with consumer stopped (Step 9), or confirm producer returns 202 accepted.

Wrong Splunk org / realm

Match SPLUNK_INGEST_URL to the realm you use to sign in (us0, us1, eu0, etc.).

Teardown

Stop and remove volumes
cd ~/projects/ibm-mq-o11y-lab
docker compose down -v

Recap: mq_otel exposes IBM MQ metrics; Splunk Metrics shows queue depth and related signals for operations and alerting.
