Hands-on lab · IBM MQ · Splunk Observability Cloud

IBM MQ → Splunk Observability Cloud

Run a local IBM MQ queue manager with Node.js producer and consumer apps, export MQ infrastructure metrics via mq_otel, enable the MQ OpenTelemetry tracing exit, and send application traces and logs through the OpenTelemetry Collector into Splunk Observability Cloud (APM, Metrics, Log Observer).

Step 1~5 min

Prerequisites

  • Docker Desktop (8 GB+ RAM recommended)
  • Node.js 20+ for npm run load-traffic
  • Splunk Observability Cloud ingest token in .env.splunk
  • Accept IBM MQ license via LICENSE=accept (developer/education)
  • Copy secrets/mqAppPassword.txt for the mq_otel exporter

Ports: 1414 MQ, 9443 console, 8080 producer, 8091 workshop, 4317/4318 OTLP.

Step 2~15 min

Start the platform

Terminal
cd ~/projects/ibm-mq-o11y-lab
cp .env.example .env
cp .env.splunk.example .env.splunk
cp secrets/mqAppPassword.example.txt secrets/mqAppPassword.txt
docker compose up --build -d
bash scripts/verify-stack.sh

First build compiles Node services and the mq_otel image (UBI + IBM MQ client). Allow several minutes.

Verify collector

curl http://localhost:13133/ should return collector health JSON.

Open the MQ web console and browse Queues to confirm ORDER.REQ exists. Developer defaults also create DEV.QUEUE.* objects.

Step 4~10 min

Message flow

Submit an order
curl -X POST http://localhost:8080/orders \
  -H "Content-Type: application/json" \
  -H "X-Correlation-Id: lab-order-1" \
  -d '{"productId":"SKU-200","quantity":3}'

Watch the consumer:

docker compose logs -f order-consumer

Expected: HTTP 202 accepted and a consumer log line with Order message consumed.

Step 5~10 min

Structured logging in Log Observer

Services emit JSON logs with Splunk-compatible fields:

{
  "severityText": "INFO",
  "service.name": "order-producer",
  "deployment.environment": "ibm-mq-lab",
  "trace_id": "...",
  "mq_queue": "ORDER.REQ"
}

In Splunk Observability Cloud → Log Observer, filter:

deployment.environment:ibm-mq-lab

Click a log line and pivot to the related trace via trace_id.

Step 6~10 min

MQ metrics (mq_otel)

The mq-otel-exporter service publishes queue manager and queue metrics over OTLP. In Splunk Metrics or chart builder, search for metrics with prefix ibmmq (from metaprefix in config).

  • Queue depth on ORDER.REQ — increases during the failure demo
  • Channel status for DEV.APP.SVRCONN
  • Queue manager connection counts

Detector idea

Alert when queue depth for ORDER.REQ stays above a threshold for 5 minutes.

Step 7~10 min

MQ tracing + APM

Application spans: order-producer (mq.put.order) and order-consumer (mq.get.order).

MQ-native spans: tracing exit sends PUT/GET spans when mqtracingexit.conf is installed (see mq-tracing-setup service). After changing tracing config:

Restart QM
bash scripts/mq-tracing-enable.sh

In Splunk APM, filter environment ibm-mq-lab. Show service map linking producer and consumer; open a trace that crosses HTTP → MQ PUT → MQ GET.

Step 8~10 min

Failure demo — consumer stopped

  1. docker compose stop order-consumer
  2. npm run load-traffic -- 25 200
  3. In Splunk Metrics, watch ORDER.REQ depth rise
  4. Producer may return 503 if MQ back-pressure or timeouts occur; check ERROR logs
  5. docker compose start order-consumer — depth drains, logs return to INFO

Troubleshooting

No data in Splunk O11y

Confirm .env.splunk ingest token and realm URLs. Check docker compose logs otel-collector for export errors. Set OTEL_SDK_DISABLED=false in .env.

mq-otel-exporter exits or restarts

Ensure secrets/mqAppPassword.txt exists and matches MQ_APP_PASSWORD. Wait for MQ health before exporter starts.

Producer 503 / MQ connection errors

Verify docker compose ps shows MQ healthy. Connection name must be mq(1414) from inside Compose network.

MQ tracing spans missing

Tracing exit support varies by MQ version/platform. Run bash scripts/mq-tracing-enable.sh and generate new traffic. App-level spans still demonstrate the lab.

Teardown and wrap-up

docker compose down -v

Discuss: metrics for capacity planning (depth), traces for latency debugging, logs for payload and correlation IDs.
