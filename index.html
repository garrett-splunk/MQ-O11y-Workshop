Facilitator guide

Hands-on lab · IBM MQ metrics · Splunk Observability Cloud

IBM MQ metrics in Splunk Observability Cloud

Run a local IBM MQ queue manager, export queue and queue-manager metrics with mq_otel, and view them in Splunk Metrics. Sample apps move messages so queue depth changes; this lab does not cover APM traces or Log Observer in the exercises.

What you will do

Clone the repo, add your Splunk ingest token, start Docker Compose, run the verification script step by step, generate traffic, and chart IBM MQ metrics (especially ORDER.REQ depth).

Step 2~10 min

Splunk ingest token (.env.splunk)

Only the OpenTelemetry Collector reads this file. It forwards metrics to Splunk using your token and realm URLs.

Workshop token

In a live session, your facilitator may give you an ingest token and realm (for example us1) on a slide or in chat. Use that value in Step 2c — you do not need to create your own token unless you are self-paced.

2a — Create the file from the template

Terminal (repo root)
cd ~/projects/ibm-mq-o11y-lab
cp .env.splunk.example .env.splunk

2b — Get the token value

Option A — Facilitator-led workshop: Copy the ingest token from the workshop materials. Note the realm and ingest URLs if the facilitator lists them (often US1).

Option B — Self-paced: Create your own token in Splunk O11y:

  1. Sign in to Splunk Observability Cloud (note your realm, e.g. us1 in the URL).
  2. Open Organization Settings (gear) → Access Tokens.
  3. Choose New Token → type Ingest (not API-only).
  4. Copy the token value once; you will not see it again.

2c — Edit .env.splunk on the command line

From the repo root, open the file in a terminal editor. Pick nano (easiest) or vi.

Using nano (recommended for beginners)

  1. Run: nano .env.splunk
  2. Use the arrow keys to move to the line SPLUNK_ACCESS_TOKEN=your-ingest-token-here.
  3. Delete your-ingest-token-here and paste the workshop (or your own) ingest token immediately after the = with no spaces.
  4. If the facilitator gave a realm, set SPLUNK_REALM and the three URLs to match (see example below). For US1, the template is usually correct except for the token.
  5. Save: press Ctrl+O, then Enter. Exit: Ctrl+X.
Open with nano
cd ~/projects/ibm-mq-o11y-lab
nano .env.splunk

Using vi (vim)

  1. Run: vi .env.splunk
  2. Press i to enter insert mode.
  3. Move to the token line and replace the placeholder with your ingest token.
  4. Update realm URLs if needed, then press Esc.
  5. Type :wq and press Enter to save and quit. (To exit without saving: Esc then :q!)
Open with vi
cd ~/projects/ibm-mq-o11y-lab
vi .env.splunk

What the file should look like (US1 example)

SPLUNK_REALM=us1
SPLUNK_ACCESS_TOKEN=paste-your-ingest-token-here
SPLUNK_INGEST_URL=https://ingest.us1.signalfx.com
SPLUNK_API_URL=https://api.us1.signalfx.com
SPLUNK_LOG_INGEST_URL=https://ingest.us1.signalfx.com/v1/log

Realm must match

If your org is EU0, use ingest.eu0.signalfx.com and api.eu0.signalfx.com. Never commit .env.splunk to git. Do not share your screen while the token line is visible.

Step 8~15 min

View IBM MQ metrics in Splunk

After Step 7, allow 1–2 minutes for ingest. All series from this lab use the ibmmq prefix (see metaprefix in mq-otel-exporter/mq_otel.yaml) and are tagged with deployment.environment:ibm-mq-lab.

8a — Find metrics in the Splunk O11y UI

Use any of these paths (wording may vary slightly by UI version):

Option 1 — Metadata Catalog (best for discovery)

  1. Sign in to Splunk Observability Cloud.
  2. Open the main menu → Settings → Metric Metadata (Metadata Catalog).
  3. In the search bar, type ibmmq and pick a matching metric name from the list.
  4. Review the preview chart, metric type (gauge vs counter), and dimensions (queue name, channel name, queue manager, etc.).
  5. Use View in chart (or equivalent) to open Chart Builder with that metric pre-selected.

Splunk docs: Metric Finder and Metadata Catalog

Option 2 — Create a chart (Chart Builder)

  1. Click Create (+) in the top navigation → Chart.
  2. Set the time range to Past 15 minutes (or Past 1 hour while debugging).
  3. In the plot editor Signal field, type a metric name containing ibmmq (see naming note below).
  4. Add a filter on the plot, for example deployment.environment:ibm-mq-lab.
  5. To focus on the order request queue, add a dimension filter for queue name ORDER.REQ when that dimension appears on the series (exact key name is shown in the Metadata Catalog for your metric).
  6. Save the chart to a dashboard if you like.

Splunk docs: Create charts · Plot metrics with Chart Builder

Option 3 — Metric Finder

  1. From the main navigation, open Metric Finder (or search “metrics” in the menu).
  2. Search for ibmmq and open a result to chart it.

Metric naming in Splunk

The exporter emits OpenTelemetry names such as ibmmq.queue.depth (object type in the middle: queue, channel, qmgr, …). Splunk may display dots or underscores — search for ibmmq and use the Metadata Catalog rather than guessing the exact string.

8b — Metrics you get out of the box in this lab

The lab’s mq_otel config enables object status and $SYS publications, and monitors these objects:

  • Queues: ORDER.*, DEV.QUEUE.* (not SYSTEM.* / AMQ.*)
  • Channels: DEV.*, ORDERS.*
  • Poll interval: 15s
CategoryWhat you should seeLab exercise tie-in
Queue status Depth and related queue attributes on ORDER.REQ, ORDER.RESP, and matched DEV queues (gauges). Step 7 traffic and Step 9 failure demo — depth rises when the consumer is stopped.
Queue manager Queue manager status, connection limits, command server / channel initiator status. Confirms QM1 is healthy while the stack runs.
Channels Status and traffic-style attributes on monitored channels (e.g. bytes/buffers sent). Supports ops views alongside queue depth.
$SYS publications Platform-style metrics (CPU, memory, disk/log summaries) published under IBM’s system topics. Optional context for capacity; not required for the depth demo.
MQI statistics Per-queue mqput / mqget counters and similar statistics events. Not exported in default lab config (useStatistics: false). Enable in MQ and in YAML if you extend the lab.

Representative OpenTelemetry-style names (from IBM’s exporter; your Splunk UI may vary slightly):

  • ibmmq.queue.depth — current depth (filter to queue ORDER.REQ)
  • ibmmq.qmgr.status — queue manager status enum
  • ibmmq.channel.status — channel status on monitored channels

8c — Official metric reference (for deeper reading)

  • IBM metrics.txt — full catalog of metric classes (queue, channel, qmgr, statistics, publications).
  • IBM mq_otel README — OpenTelemetry naming (ibmmq.<type>.<metric>), counters vs gauges, OTLP setup.
  • IBM MQ docs — metrics on system topics — describes $SYS publication metrics when usePublications is enabled.
  • ibm-messaging/mq-metric-samples — source repo for mq_otel (same metrics as other collectors in that project).

8d — Chart queue depth for this lab

  1. Run sustained load (Step 7) or the Step 9 failure demo so depth moves.
  2. In Metadata Catalog or Chart Builder, locate an ibmmq queue depth metric.
  3. Filter deployment.environment:ibm-mq-lab.
  4. Filter or group by queue name ORDER.REQ.
  5. Plot as a line chart over Past 15 minutes; re-run load if the line is flat.

Metrics to discuss

Queue depth on ORDER.REQ as a backlog signal; queue manager and channel status for availability; optional $SYS CPU/disk for capacity.

Detector idea

Create a detector when ORDER.REQ depth stays above a threshold for several minutes.

No metrics? Confirm .env.splunk, restart collector, check docker compose logs mq-otel-exporter and otel-collector.

Step 9~10 min

Failure demo — queue depth (metrics only)

Stop the consumer so messages accumulate on ORDER.REQ; watch depth rise in Splunk Metrics.

  1. Stop the consumer 
    docker compose stop order-consumer
  2. Send load 
    npm run load-traffic -- 25 200
  3. In Splunk O11y — follow Step 8: Metadata Catalog or Chart Builder, filter deployment.environment:ibm-mq-lab, chart ORDER.REQ depth.
  4. Restore processing 
    docker compose start order-consumer
  5. Confirm depth trends down as the consumer drains the queue.

Troubleshooting

Cannot connect / MQRC_UNKNOWN_CHANNEL_NAME / mq-otel-exporter Restarting

The metrics exporter and apps connect on channel DEV.APP.SVRCONN. If an old MQ data volume was created without dev objects, that channel may be missing.

Fix: rebuild and recreate the stack so lab MQSC runs on startup:

cd ~/projects/ibm-mq-o11y-lab
git pull
docker compose up --build -d
docker compose logs mq-otel-exporter --tail 20

If it still fails, reset the queue manager volume (destroys local MQ data):

docker compose down -v
docker compose up --build -d

Confirm secrets/mqAppPassword.txt matches MQ_APP_PASSWORD in .env (default passw0rd).

Cannot find MQ C library on order-producer / order-consumer

On Apple Silicon, services run as linux/amd64 images with the MQ client installed. Rebuild after pulling latest:

docker compose build --no-cache order-producer order-consumer
docker compose up -d order-producer order-consumer
No IBM MQ metrics in Splunk

Verify .env.splunk token and realm URLs. Run docker compose up -d otel-collector. Check docker compose logs mq-otel-exporter and docker compose logs otel-collector. Ensure secrets/mqAppPassword.txt exists.

verify-stack.sh fails on health checks

Run docker compose ps and docker compose logs mq. MQ can take ~60s on first start. Re-run the script after MQ is healthy.

Flat queue depth chart

Run npm run load-traffic with consumer stopped (Step 9), or confirm producer returns 202 accepted.

Wrong Splunk org / realm

Match SPLUNK_INGEST_URL to the realm you use to sign in (us0, us1, eu0, etc.).

Stop and remove volumes
cd ~/projects/ibm-mq-o11y-lab
